# Windows 桌面应用分析与改进

目标分支：`trae/agent-ctCMlg`，基线提交 `19298f2ad223e16d3de5cd6cce1c7a940bb5e0f9`。

## 产品定位

这是账号操作与资源分配工作台，核心流程是「导入资源 → 创建账号记录 → 检查关联资料 → 导出 AdsPower」。原有深色界面与操作密度适合桌面使用，主要短板是缺乏真正的桌面生命周期和数据文件保护。本轮没有重写成熟解析器或把产品替换为另一个仪表盘。

## 本轮落实

| 领域 | 原有问题 | 实现结果 |
| --- | --- | --- |
| 桌面运行 | 依赖手动启动 Node 服务与访问浏览器 | Electron 自动启动本机服务、动态端口、单实例、原生菜单和 Windows 构建 |
| 桌面边界 | API 无桌面访问限制 | 每次启动独立令牌、只监听 loopback、渲染器沙箱及隔离、限定 IPC、阻止外部导航 |
| 持久化 | 损坏 JSON 被忽略后使用空数据；写失败可能留下内存改动 | 损坏时阻止启动、原子写入、磁盘失败时回滚、自动备份及原生恢复 |
| 资源分配 | 无效重新关联可能释放旧资源；可重复使用占用资源 | 先校验再改动、禁止重复分配独占资源、阻止删除使用中的资料 |
| 创建记录 | 无重复指纹与域名批次保护 | 拒绝冲突批次、上限 500 条、失败不占用资源 |
| 营业执照 | PDF 仅提取文本；不识别丹麦证书的无标签布局 | 导入前字段校对、证书信息识别、原件存储及内容校验、详情面板与系统阅读器 |
| 连接体验 | 等待或失败时没有恢复路径 | 明确加载状态、错误提示、连接重试、Ctrl+R，失败时保留已有页面 |
| 环境 | Node 18 声明与 PDF 依赖的实际要求不一致 | Node 22.13+，锁定桌面构建依赖和可重复回归脚本 |

## 架构选择

桌面窗口继续使用现有 HTML/CSS/JavaScript，Node 服务与 Electron 主进程共用受控生命周期。所有写操作在同步事务包装中运行，验证成功且磁盘保存完成才提交；没有启动第二个应用实例共同写同一数据目录。

保留 JSON 数据格式，以便兼容旧版数据与便携的完整备份。PDF 被去重后随快照保存，避免“资料已恢复但附件路径指向另一台机器”的问题。该方案适合有限规模的个人工作台；大量扫描件或多用户并发应单独规划 SQLite 与附件目录迁移，不能宣称本版支持这些场景。

## 发布验收仍需完成

- 在 Windows 10/11 x64 验证安装、升级、卸载保留数据和默认 PDF 阅读器。
- 用真实日常格式验收代理、信用卡与 AdsPower 导出；不要把仅有的示例格式当成全部供应商兼容证明。
- 正式分发前配置发行者代码签名，并决定自动更新渠道。
- 如需加密保存密码、2FA 或卡片数据，另行设计 Windows DPAPI 与备份密码机制；当前显示隐藏不等于磁盘加密。
- 扫描 PDF 的 OCR、跨设备同步和团队协作不在本轮实现范围。
