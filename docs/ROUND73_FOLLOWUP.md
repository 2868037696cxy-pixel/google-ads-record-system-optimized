## 3. F08 的具体行为

输入：

```text
组织名称：Orchid Seven ApS
城市：Copenhagen
CVR: 00123456
```

预期关键字段：

```json
{
  "name": "Orchid Seven ApS",
  "city": "Copenhagen",
  "cvr": "00123456"
}
```

修复点：

1. `LIC_LABELS` 增加注册号项；它也进入 `LIC_STOP`，成为前一个字段的停止边界。
2. `parseLicenses()` 返回 `cvr`，而不是提取后丢弃。
3. 支持注册号、公司/企业/商业注册号、登记号、统一社会信用代码、CVR、CVR number/nr./no.、Registration number、Business registration no. 等标签。
4. 保留编号中的字母、连字符和前导零；解析阶段不擅自转成数字。
5. 标签要有起始或分隔边界，不能将 `Electricity:` 中的 `city:` 当作城市标签。
6. 覆盖字段前后顺序、同行分隔、多行输入、缺少注册号，以及原来的纯名称逐行导入。
7. 实际把解析结果保存后，由另一账号用不同名称提交相同注册号，确认触发全员冲突且不泄露原所属人。

本轮没有新增国家/机构字段，也没有宣称已经完成国际企业身份标准化。

## 4. 两项不能误判为已彻底解决的问题

### 4.1 F09：文件头尾不等于有效 PDF

旧补丁加 `%%EOF` 后，仍可构造带正确头尾但不存在页面/目录结构的文件。本轮在最终导入入口调用已有的受并发和页数限制的 PDF 解析函数，解析失败不进入数据库事务。

这解决的是“最终写入只验魔数”的缺口，不等于病毒扫描、恶意 PDF 完整检测、OCR 或历史文件批量清洗。读取旧备份时的结构验证是另一个入口，不能自动记为已覆盖。解析繁忙必须保留原 429 提示，不伪装成文件损坏。

### 4.2 F11：小备份成功不能证伪大备份失败

旧代码的个人备份把 PDF 转成 Base64 放入 JSON，再把加密后的内容转成 Base64；导入恢复限制仍为 64MiB。此前约 3KB 的成功往返未覆盖这个条件。

本轮负向验证通过正式 HTTP 入口上传 5 份约 8MiB 的有效合成 PDF，旧代码导出返回 200，但实际恢复超限失败；修复后在导出时返回明确的 409，不提供一个看似有效却无法恢复的下载文件，原数据不变。

实现：

- 统一恢复与导出预算，保留少量外层封装余量。
- 先按原件大小判断必然超限的情况，避免无意义地解密、展开全部文件。
- 再检查真实加密 envelope 的 UTF-8 字节数，包含记录与 JSON 开销。
- 校验通过后才设置下载响应头。
- 正常大小的 v2 个人备份格式保持不变。

**尚未完成：**可承载任意规模的个人备份任务、分块传输、断点续传和隔离暂存恢复。大规模用户当前仍须由管理员使用现有流式加密全库备份维护流程；全库备份不能交给普通员工浏览，也不能据此声称个人大备份体验已经完成。

## 5.1 F12 / F25 / F26 / F06 后续收口

### F12：版本不能再省略

记录与资源的 PATCH 现在都把 version 当成写入前置条件。缺失、null、字符串、小数或负数统一返回 428；只有合法整数且与当前行一致才允许写入，陈旧版本仍返回 409。资源 PATCH 同时修改状态和字段时只把 version 增加一次，避免版本语义漂移。

### F25/F26：回滚与维护互斥

部署和定时备份共用 `/var/lib/adsworkbench/.maintenance.lock`。部署会非阻塞取得锁，备份服务最多等待 300 秒，从而避免迁移/切换发布目录时和 SQLite 备份重叠。故障注入在 current 链接已经切换、备份 unit/timer 已写入之后主动失败；回滚会停止新备份任务，恢复数据、env、主服务 unit、备份 unit/timer、current 链接、原 enabled/active 状态，并等待旧服务健康后才返回。验证只在一次性 CI systemd 主机执行，没有向生产环境注入故障。

### F06：非拉丁名称与跨字段判重

企业名称归一化由 ASCII-only 改为保留 Unicode 字母/数字，因此中文、日文、希腊文、西里尔文等不再得到空键。组织名称和法定名称使用同一身份集合交叉比较，例如旧资料 legal_name 等于新资料 name 也能判重。历史 `dup_name/dup_legal` 为 NULL 的行会尝试补算；若补算会与已有组织/法定名称交叉冲突则保持原状并进入人工核对报告，不自动覆盖。内部重复审计也使用同一交叉身份维度。

F06 解决的是“名称层面的 Unicode/跨字段漏判”，**不等于 F05 已解决**。注册号仍缺显式司法辖区/登记机关命名空间，多国家同号场景必须另做数据模型和迁移设计。
