# F04 复现记录：相近公司名覆盖注册号

第 58 轮实测复现。**这是 P1 级数据完整性缺陷，尚未修复。**

## 现象

同一账号连续导入两家注册号不同、但名称归一化后相同的公司：

```
A 导入: 200 {"added":1,"updated":0,...}
A 后:   [{"id":1,"name":"Example Orchid ApS","cvr":"DK11111111"}]

B 导入: 200 {"added":0,"updated":1,...}      ← 被判为"更新既有行"
B 后:   [{"id":1,"name":"Example Orchid Ltd","cvr":"DK22222222"}]
```

**A 的注册号 `DK11111111` 被 B 的 `DK22222222` 覆盖了。**
行数仍是 1，从计数上看不出任何异常。

## 为什么危险

注册号是企业的身份标识。两家注册号不同的公司是两家不同的公司，但系统按
"归一化公司名"把它们判成同一家，并用后者的数据**整体覆盖**了前者：

- 原公司的注册号消失，且没有任何 409 / duplicates / conflicts 提示
- 计数不变（`added:0, updated:1`），运营不会注意到
- 一旦覆盖，除非有备份，原注册号无法找回

## 与第 34 轮"证伪"的区别（重要）

第 34 轮我测的是**同注册号、不同名称**：

```
A Alpha Holding ApS / DK11111111
B Beta Trading ApS   / DK11111111   → 409，判重依据：组织名称，行未变
```

那种形状确实被正确拦下，我据此写了"F04 批量路径已证伪"。**但那种形状不是审计描述的
问题。** 审计说的是「相近公司名」覆盖注册号——即**名称相近而注册号不同**。

两种形状走的是不同分支：

| 形状 | 结果 |
|---|---|
| 注册号相同、名称不同 | 409 ✅ 正确拦截 |
| **名称归一化相同、注册号不同** | **200 updated:1 ❌ 覆盖注册号** |

## 根因方向（未证实）

`server.js` 批量导入循环里，命中既有行后的更新分支：

```js
updatePoolRow(..., {...store.toPublic(mine), ...it})
```

`it` 是 `normalizeImport()` 归一化后的导入项（`server.js:608` 会把缺失字段填成
空字符串）。展开顺序意味着 `it` 里非空的字段**无条件覆盖**既有行——包括注册号
`cvr` 和由它派生的 `dup_cvr`。

缺口在于：命中既有行的判据是"名称归一化相同"，但**没有校验两行的注册号是否一致**。
注册号不同时应当判为冲突（409 / conflicts），而不是当作更新。

`rowMatchesKeys(row, keys)`（`lib/dedup.js:79`）只在 `['dup_cvr','dup_name','dup_legal']`
里做 any-match，同样不区分"名字相同但注册号不同"这种矛盾情形。

## 修复要点（下一轮）

1. 在命中既有行、准备 update 之前，比较 `mine.cvr` 与 `it.cvr` 的归一化值：
   两者都非空且不相等 → 判为冲突，写入 `conflicts` 并跳过，不写库。
2. 单条导入路径（`server.js:1350/1388/1399`）与批量路径共用这段逻辑，改一处即可。
3. 测试必须用**两种形状**：同号不同名（应 409）、同名不同号（应冲突且行不变），
   并断言整行 JSON 前后一致。

## 验证命令

本记录的数据来自一次性探针（运行后已删除）。重跑方式：注册 → 导入 A
（`Example Orchid ApS` / `DK11111111`）→ 导入 B（`Example Orchid Ltd` /
`DK22222222`）→ 读 `/api/bootstrap`，检查 `pools.licenses[0].cvr` 是否由
`DK11111111` 变成 `DK22222222`。
