# 广告账号管理工作台：个人数据隔离 + 全团队文件查重

> 最终需求：**3 位或更多成员独立登录；每个人只看自己创建/归属的记录；整个团队不能保存重复的文件。**
>
> 当前提交对现有 SQLite 多用户实现补强了 PDF 查重、隐私和个人备份校验。下文 PostgreSQL 是长期架构蓝图，不表示已上线。

## 一、业务规则（以此作为验收标准）

| 操作 | A | B | C |
|---|---|---|---|
| 登录后列出账号记录 | 仅 A | 仅 B | 仅 C |
| 查看邮箱/代理/支付资源/营业执照 | 仅本人 | 仅本人 | 仅本人 |
| 下载他人 PDF | 拒绝 | 拒绝 | 拒绝 |
| 上传已被团队任一成员保存的同一 PDF | 409 拒绝 | 409 拒绝 | 409 拒绝 |
| 修改文件名但内容相同 | 同样拒绝 | 同样拒绝 | 同样拒绝 |
| 同组织名称/注册号但不同文件 | 提示全员资料重复 | 同样处理 | 同样处理 |
| 查重返回别人的公司资料/用户名 | 不允许 | 不允许 | 不允许 |
| 恢复个人备份 | 仅替换本人数据 | 仅替换本人数据 | 仅替换本人数据 |

文件“相同”优先按文件原始字节 SHA-256 判断；不比较文件名，因为重命名不能规避。**不同扫描质量、另存成其他 PDF 导致字节不同**，还需要注册号与归一化名称双重核对；文件特征值不能取代业务资料查重。

**自己曾经上传过的同一个 PDF，也不能再次执行“新导入”。**本人历史备份恢复属于容灾替换，不是新建记录，可按独立路径允许，但需要检测是否与其他成员当前数据冲突。

## 二、推荐存储模型

生产长期推荐 PostgreSQL，保持“团队唯一查重 + 个人数据归属”两套互不混淆的规则。

- `teams` — 团队，每个团队一个查重范围。
- `users`、`team_members` — 登录身份、成员关系。服务端从 session 识别。
- `account_records` — 账号记录包含 `team_id` + `owner_id`；普通用户只能查自己的行。
- `resources` — 本人独立的邮箱、代理、支付令牌和营业执照资源，带 `owner_id`。
- `file_registry` — **全团队唯一查重账本**，`UNIQUE(team_id, sha256)`。普通用户无列表接口，仅能触发“已存在/不存在”校验。
- `business_licenses` — 公司名称/注册号规范化后，在团队内唯一；保留原始公司元数据在所属人的私有表中。
- `audit_events` — 安全审计，不写密码、卡号、2FA 原文或其他用户敏感字段。

原 PDF 字节存在私有对象存储，数据库只存 `object_key`、hash、大小和内容类型；文件通过身份校验后的后端接口下载，不生成公开链接。

## 三、双层防重

1. **客户端上传预检查**：服务端计算 sha256，查同一团队的 `file_registry` 是否已有。若已存在，立即返回 `409 DUPLICATE_FILE`，不给归属用户名、公司名或其他资料；客户端保留醒目提示。
2. **最终提交**：在数据库事务里插入文件查重账本，`(team_id, sha256)` 唯一索引阻止多人同时通过预检查后双写。注册号、企业名称的唯一约束是第二道防线。
3. **批量文件**：先全部校验，任意一份冲突则整批拒绝或明确列出可跳过项；若选择整批处理，必须完整回滚，不能部分落库。
4. **恢复备份**：在修改本人记录之前，校验备份中的每个 PDF 都没有占用别人的全局查重键。失败整个恢复回滚且保留自己的现有数据。
5. **删除/归档**：业务是否允许重新导入已删除文件需单独定规则。默认**保留 file_registry 已用指纹作为防重墓碑**（标记已撤销但不清除 hash），避免删掉后反复提交；管理员审核解除占用时单独记录操作。

## 四、真实用例

- A 上传丹麦公司 `Example ApS` 的 `company.pdf`，保存成功。
- B 登录，自己的列表看不到 A 的组织资料。B 上传完全相同内容但叫 `new.pdf`，系统提示“该文件已存在，不能重复保存”，不展示 A 的身份信息。
- C 上传另一份内容不同的 PDF，但注册号与 A 相同，系统提示“公司注册号重复，已拒绝保存”。
- C 上传真正不同的公司材料，保存到 C 自己的账号中，A 和 B 看不见。

## 五、当前分支与后续建设

当前 `feat/team-console-ui-data-architecture`：
- 现有 SQLite `owner_id` 读写隔离不变；
- 营业执照 PDF 在识别前与保存事务内进行 SHA-256 全员判重；
- 冲突说明只含类别与当前输入，不再暴露别人的用户名、原件/公司信息；
- 普通用户不能读取全体证书明细审计；
- 个人备份恢复不能绕过他人 PDF 占用，并保护原件关联；
- UI 已添加“运营总览”、按资源类别保留筛选，以及安全的文件冲突提示。

本次 SQL 仅供迁移设计。**不能直接应用到当前 SQLite 正式数据**。未来如果启用多个独立企业空间，团队之间的文件查重应该以 `team_id` 分界，避免不同公司的敏感业务相互泄漏。

## 六、安全边界

现有旧版仍存在明文凭据/支付卡敏感字段的存储设计。团队正式上线前必须改为安全凭据服务和最小权限访问，并**禁止存储 CVV/CVC**。隐藏字段只是 UI，不是加密保护。上线前检查日志、导出、备份和客户端 HTML 的泄露风险，默认不允许跨账号的全局查重列表。

## 七、回归清单

- 三个人的记录、资源及 PDF 互不可读；直接猜 ID 访问返回 404/403。
- 同一 PDF 重命名后跨账号/本人再次上传均返回 409，文件、账号数据未新增。
- 企业名称/注册号重复时 409 但不会泄露其他用户详情。
- 两名成员同一时刻保存同一 SHA，最终只有一份落库。
- 含别人 PDF 的备份恢复失败，原本人数据不受影响。
- 普通账号访问全体查重报表返回 403。
- 批量导入某一项重复时完整回滚；重复检测不依赖客户端筛选。
