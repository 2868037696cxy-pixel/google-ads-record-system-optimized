# 多人协作广告账号工作台 — 数据架构与上线方案

> 状态：**架构设计稿，不是已启用的共享数据库**。本分支基于 `feat/multiuser`，当前运行代码仍使用 SQLite + `owner_id` 个人隔离。本方案以团队协作为目标，必须完成后端权限、迁移和安全回归，才能切换到共享数据。

## 1. 产品边界与协作模式

这是“账号及基础资源管理系统”，不应和广告花费/ROI 日报混为一谈。核心流程：导入邮箱/代理/付款工具引用/营业执照 → 校验与去重 → 批量创建账号记录 → 分配资源 → 团队维护状态和交接 → 导出授权范围内的数据。

**三种归属必须独立**：
- `workspace_id`：租户数据边界；同一个工作空间可供多人授权协作；不同工作空间一律隔离。
- `created_by` / `updated_by`：操作者，用于追责审计，不等同于资源所有人。
- `assignee_id`：账号记录负责人，可转交；不改变资源所属工作空间。
资源库归工作空间所有，资源占用由关联表表示，不能通过修改个人 `owner_id` 模拟共享。

默认一个公司一个 workspace；超级管理员可以建立第二 workspace，实现隔离。例如“广告组 A”“广告组 B”可以属于同一 workspace，通过标签或团队权限进一步分组。单个工作空间内部的可见范围由权限控制；**共享不等于人人能看所有密码/凭据**。

## 2. 技术栈选型

| 层 | 建议 | 原因 |
|---|---|---|
| Web UI | 保留原生 HTML/CSS/JS，先模块化；可未来改 React | 延续成熟批量录入和 CSV/AdsPower 流程 |
| API | 保留 Node/Fastify，集中鉴权与校验 | 与现有服务兼容、减小迁移面 |
| 主库 | 生产协作优先 PostgreSQL 16+ | 并发写入、行锁、备份与迁移工具成熟 |
| 小团队过渡 | 仅后端单实例访问 SQLite WAL，严禁多个客户端直接写库 | 适用于短期验证，不建议当作长期多实例共享数据库 |
| PDF 原件 | 私有对象存储（如 S3 兼容桶），记录 sha256/size/key | 不放 base64 到主库；访问采用 API 授权后短期签名 URL |
| 敏感凭据 | KMS/密钥管理 + 应用层信封加密 | 邮箱密码、2FA 种子、代理密码不可明文存储 |
| 支付信息 | 支付服务商令牌/别名/末四位/有效期 | **禁止存储 CVV**；不要把完整 PAN 放进普通数据库或 CSV |
| 备份 | PostgreSQL 自动备份 + WAL/PITR + 对象存储版本管理 | 目标明确的 RPO/RTO 与演练恢复 |
| 任务 | 异步任务表/队列 | 大批量导入、导出、PDF 解析避免 HTTP 超时 |

## 3. 核心表设计

参见 `docs/team-workspace-postgres.sql`（**新系统建库蓝图，不得在现有 SQLite 库执行**）：

- `workspaces`：企业/团队工作空间
- `users`、`workspace_members`：成员关系与角色（owner/admin/operator/viewer）
- `ad_accounts`：账号台账，保存国家、产品、域名、指纹、运营状态、负责人、版本号
- `resources`：邮箱/代理/营业执照/支付令牌等通用资产元数据，**不直接存敏感明文**
- `resource_assignments`：账号与资源的关联，独占资源同一时间只允许一条有效关联；代理可按明确策略共享
- `license_profiles`：组织名称、法定名称、注册号、地址，以及证书对象引用
- `file_objects`：附件 sha256/大小/存储 key/上传人
- `audit_events`：谁在何时对哪个工作空间/记录做了什么；无密码、无卡号、无 PDF 内容
- `idempotency_keys`：双击创建和网络重试去重
- `outbox_events`：提交事务内写入，再异步投递通知/同步任务

核心约束：
- 每张业务表都必须带 `workspace_id`，索引一般以 `workspace_id` 为第一列。
- `ad_accounts` 的 `(workspace_id, fingerprint)` 唯一，域名可额外定义去重策略（按国家/产品范围）。
- 对关联关系使用复合外键 `(id,workspace_id)`，防止不同 workspace 的 ID 混用。
- `resource_assignments` 的活跃独占行建立部分唯一索引：`UNIQUE(resource_id) WHERE released_at IS NULL AND is_exclusive`。
- 物理删除留有软删除窗口；对占用中的资源拒绝删除，统一释放后才能归档。
- 并发分配在数据库事务中使用 `SELECT ... FOR UPDATE SKIP LOCKED`；不足则**整批回滚**，不得部分成功。
- 数据更新采用版本字段 `version`；过期修改返回 HTTP 409，展示“其他成员已更新”，不要静默覆盖。
- 共享代理只有在资源 `share_policy=shared` 时才允许多人关联；严格禁止独占资源绕过唯一占用。

## 4. 权限矩阵

| 操作 | owner | admin | operator | viewer |
|---|---|---|---|---|
| 查看业务账号/非敏感资源 | ✓ | ✓ | 按授权范围 | 按授权范围 |
| 导入、批量创建、编辑状态 | ✓ | ✓ | ✓ | ✗ |
| 自动分配/释放资源 | ✓ | ✓ | ✓（受资源范围限制） | ✗ |
| 删除资源与批量恢复 | ✓ | 受策略限制 | ✗ | ✗ |
| 添加成员/变更角色 | ✓ | ✓（不得提升到 owner） | ✗ | ✗ |
| 查看解密后的凭据 | 需敏感权限 | 需敏感权限 | 默认无权，按需单独授权 | ✗ |
| 导出包含敏感字段的数据 | 按审批策略 | 按审批策略 | 默认不可 | ✗ |
| 全量工作空间备份 | ✓ | 可授权 | ✗ | ✗ |

后端每个请求必须：鉴别 session → 解析当前 workspace → 查 `workspace_members` → 检查操作权限/资源范围 → 加 `workspace_id` 数据约束 → 写审计。前端隐藏按钮**不是**权限校验。

## 5. 批量创建的原子流程

1. 接收 `workspace_id`、操作者、幂等 key、输入国家/产品/域名/数量/选取策略。
2. 检查 operator 权限、请求大小、域名与指纹合法性；预览结果不等于预分配成功。
3. 开启事务，锁定幂等键与选中资源；从同工作空间取未分配的资源行，`FOR UPDATE SKIP LOCKED`。
4. 验证资源状态、共享策略、数量与唯一索引；不足时 409 返回每类缺口。
5. 插入账号记录、资源关联、状态变更、审计事件和 outbox，最后一次性提交。
6. 返回所创建 ID 和状态；失败则整批回滚，不留“半创建”记录。
7. 前端显示最终结果与缺口，保留输入草稿，并提供仅管理员可使用的重新分配工具。

## 6. 保密与合规的硬约束

现有 `feat/multiuser` 代码**将邮箱密码、代理凭据、2FA 秘钥及付款卡的 CVV 明文放入 SQLite 和记录快照**，这不能直接照搬到多人共享的正式系统。

- **任何时候都不存 CVV/CVC**；若需处理完整卡信息，必须评估 PCI DSS 范围并交给合规支付/发卡服务提供令牌，别做自制“信用卡保险库”。
- 仅返回脱敏账号、令牌别名、卡末四位。密码/2FA 种子只经专门授权解密接口返回，默认不发给浏览器。
- 不允许把明文凭据写入日志、搜索索引、UI `data-*` 属性、URL、通知或常规 CSV 备份。
- 敏感操作应有单独的凭据访问审计、短时二次确认、最小权限和可撤销授权。权限调整后需要使旧会话/凭据授权立即失效。
- 对象存储使用私有桶、服务端密钥管理、限制下载时间、附件病毒扫描与保留策略。
- 部署启用 HTTPS、Secure+HttpOnly+SameSite Cookie、严格 CSRF、强口令+MFA、限速、IP/组织访问限制。开发环境禁止复制真实密钥。
- 跨团队“营业执照重复”默认只回匿名冲突状态，**不要泄露其他团队的负责人及公司资料**；允许管理员在审计视图查看归属。

## 7. 备份与容量建议

示例初期规模（规划参数，不是现有数据）：10–30 人，10 万条账号记录、百万条审计事件、数千 PDF。PostgreSQL 基础设施可按实际监控扩容。
- 数据库：每日全量/连续 WAL 归档（依云厂商能力），每日验证自动备份成功。
- 对象：加密私有桶 + 生命周期与版本；不要把 PDF base64 存储在账号表里。
- 恢复：每月至少一次隔离环境恢复演练，清晰记录目标 RPO（如 15 分钟）/RTO（如 2 小时），根据预算确定而不是宣称已经实现。
- 日志：结构化日志无凭据，审计事件至少按内部保留政策存储，支持负责人/时间筛选。
- 导出：可筛选范围、有限期链接、导出水印、审批和审计，默认**不包含敏感列**。

## 8. 从当前 SQLite 多用户版本迁移

**禁止直接覆盖现有库；现有分支不能因为写入了本设计文档就被称作共享工作空间系统。**

1. 冻结新特性、备份 `workbench.sqlite`（包含 WAL）及完整附件，检查完整性。
2. 建立 staging PostgreSQL，导入旧 `users`；根据成员映射建立 workspace 和 `workspace_members`，管理员确认哪些数据需要共享。
3. 将旧 `owner_id` 映射至 `created_by`，将所有资源/记录指向确认的 `workspace_id`。为原 owner 创建初始负责人；每条记录保留 old_id 到 new_id 的映射。
4. 将旧快照中的邮箱密码/2FA/代理密码转为受控 secret vault 引用；卡片数据改为支付服务商令牌与末四位。**不要迁移 CVV**。
5. PDF 从数据库 BLOB 转储私有对象存储，校验 sha256；记录只存 object_key。保留原始旧库离线加密归档直到验收通过。
6. 执行冲突检测：跨 owner 重复资源、域名/指纹、营业执照公司名/注册号；先出人工核对清单，不自动吞并或删除。
7. 分阶段开启新 API：读 → 导入 → 创建 → 编辑与释放 → 导出；进行多成员并发与越权测试。
8. 双人复核数据总量、资源占用、账号关联、下载附件、权限边界；安排停机切换与回滚方案。
9. 关闭旧系统写入口，观察审计、错误率、性能后正式发布。

## 9. 发布验收必测

- A、B 同时分配最后一条邮箱，仅一个成功，另一个获得明确资源不足提示。
- A 是 viewer，直接调用写入 API 返回 403；B 无权读取另一工作空间的资源返回 404/403。
- A 修改记录后 B 用旧版本覆盖得到 409，而不是覆盖成功。
- 成员被移除后旧 session 立刻无权继续请求资源。
- 创建接口超时重试并带相同幂等 key，不会生成重复账号。
- 恢复旧备份只在对应 workspace 生效，不能写掉别的团队数据。
- 敏感凭据不会出现在通用日志、审计 payload、CSV、普通页面 HTML 或资源搜索结果。
- 营业执照跨工作空间查重结果不会泄露其他团队用户名。
- 1000 条资源/10000 条记录下筛选、分页、并发写入与迁移回滚可用。

## 10. 实施里程碑

- **P0 基础安全**：禁存 CVV、秘密隔离、权限设计与工作空间边界、独占分配事务和审计。
- **P1 数据迁移**：PG schema/导入脚本、附件对象存储、成员邀请及迁移核验。
- **P2 核心协作**：共享资源、负责人、批量操作、冲突提示、记录活动流、权限控制 UI。
- **P3 产品体验**：工作台总览、任务通知、全局搜索、CSV/AdsPower 受限导出、桌面端兼容。
- **P4 生产运营**：备份恢复、监控告警、压力测试、桌面签名与发布流水线。

**本次 GitHub UI 变更仅为预先优化界面及流程，不意味着 P0–P4 已全部实现。**
