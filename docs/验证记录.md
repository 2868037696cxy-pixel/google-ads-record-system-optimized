## 二、已修复的真实缺陷

每一条都有可失败的测试，不是"看着改了"。

### 1. 鉴权绕过（P0，第 0 优先级）

**绝对形式请求行** `POST http://<host>/api/backup/restore` 可以完全绕过鉴权钩子。
根因是钩子里用 `req.url.startsWith('/api/')` 判断是否需要鉴权，而 `req.url` 在
绝对形式下是完整 URL，不以 `/api/` 开头 → 直接 `return`，鉴权被跳过。

**同一根因的第二个入口**：`GET /%61pi/bootstrap` 返回 200 且带数据。
路由用的是**解码后**的路径，鉴权用的是**未解码**的 `req.url`，两者不一致。

**修法**：显式要求 origin-form；解码路径并显式捕获解码失败（返回 400）；
限流与 `PUBLIC_PATHS` 一律改用解码后的 `pathname`。

**测试**：`tests/security.test.js` 用**原始 `net` 套接字**构造请求。
这一点不能省——`fetch` 无法构造绝对形式的请求行，URL 解析还会重写百分号编码，
用它测不出真东西。

### 2. 「第一个用户」归属回退

`resolveDefaultOwner()` 在缺少账号上下文时回退到
`SELECT id FROM users ORDER BY id LIMIT 1` —— 任何未显式传 owner 的调用都会
静默地把数据写到**第一个注册的用户**名下。

**修法**：非桌面场景直接抛错，拒绝推断归属。
（已核对全部调用点：只有 `desktop/main.js` 会省略 owner。）

### 3. 畸形请求体静默写入空记录

`POST /api/records` 对 `null`、`"a string"`、`123`、`[1,2]`、`true`、`{}`
一律返回 **200 并写入一条记录**（国家/产品/域名皆空，指纹自动生成）。

两层根因：路由层没有对象校验；且
`if (!domains.length && (typeof count === 'boolean' || ...))` 在 `count` 默认取 1 时
**恒为假**。

**修法**：路由层统一校验「必须是 JSON 对象」；补齐 `count` 的整数与范围校验。

### 4. 两个 PATCH 在畸形请求体上返回 500

`PATCH /api/records/1` 传字符串 → `updateRecord` 去迭代字符串的键 → 非法列名；
`PATCH /api/pool/:type/:id` → `'status' in body` 抛 `TypeError`。
两者都把客户端的错误变成了 500，而且是在写入路径上。

**修法**：进入 `mutate` 之前先做对象校验；去掉 `req.body || {}` 这种把
"缺体"伪装成"空对象"的写法。

### 5. 删除操作完全没有审计留痕

审计表覆盖了 `records.create`、`export.credentials`、`backup.export/restore`、
`secrets.unlock`、`password.change`，**唯独没有任何删除与修改的痕迹**。

在多人共用同一份数据的工作台里，「这条记录是谁删的」是必然会被问到的问题，
而删除不可逆——没有审计就只能回答"不知道"。

**修法**：`PATCH /api/records/:id` 记 `records.update`；
`DELETE /api/records/:id` 与 `POST /api/records/batch-delete` 记 `records.delete`。
删除类**只在确实删掉了东西时**才写，避免"点了删除但什么都没删"把有效操作淹没。

## 三、核查过、确认没有问题的

这一节的结论和第二节同等重要——它把"应该没问题"变成了"验过没问题"，
也避免了后来者把同一处再查一遍。

### 1. 跨账号越权写：没有越权

攻击者拿到受害者的真实 id 后尝试 6 条路径：

```
PATCH  /api/records/1            → 400   正确拒绝
PATCH  /api/records/1  (name)    → 400   正确拒绝
DELETE /api/records/1            → 200
POST   /api/records/batch-delete → 200
PATCH  /api/pool/emails/1        → 400   正确拒绝
DELETE /api/pool/emails/1        → 200
```

受害者的记录数、资源数、状态、名称**一个字节都没变**。
删除类返回 200 是因为它删了 0 条——既不破坏数据也不泄露信息。
**对不属于自己的 id 返回 200 是可接受的幂等语义**（省掉"重复删除报错"），
因此不判定为越权。

测试先断言数据完好、再追究状态码：顺序反过来的话，
「数据真的被改了」这个远为严重的可能性会被状态码断言挡在后面。

### 2. 全员查重：按业务字段生效，不只是按文件哈希

两份 PDF 的**行内容与文件名都不同**（字节因此不同），**只有 CVR 相同**：

```
firm-a  alpha-original.pdf  CVR 31415926  → 200
firm-b  alpha-resaved.pdf   CVR 31415926  → 409   ✓ 跨账号判重
firm-b  beta.pdf            CVR 27182818  → 200   ✓ 反向断言
全局落库 2 条
```

为什么专测这个：只按 SHA-256 去重的话，同一份执照**重新保存一次**字节就变了，
于是能重复入库，而表面上"已经做了查重"。此前的并发上传用例即使只按哈希去重也会通过。

**反向断言不可省**：没有它，一个"一律返回 409"的实现也会让用例通过——
那样的查重是坏的，却会显示为全绿。

### 3. 判重维度与地址模式

契约取自 `lib/dedup.js` 的 `chosen` 链（另有 `rowMatchesKeys` 独立印证）：

```
CVR / 组织名称 / 法定名称  → 任何模式下都硬拒
街道地址                  → 只有 DEDUP_ADDRESS_MODE=reject（默认）才硬拒
```

实测：名称相同、CVR 不同 → 409；仅地址相同、名称与 CVR 都不同（warn 模式）→ 200。

**方案里「疑似冲突转待核对」的真实语义是：不拦、让数据进库，
再由巡检（`auditLicenses`）按维度把重复组标出来——不是返回一个"待核对"状态。**
这个设计不直观，容易被误读成漏判。

### 4. 并发保存：恰好一个生效

两个请求携带**同一个** version 并发修改：

```
返回码   [200, 409]                       恰好一个成功
最终值   赢家写入的完整值                   不是两个值的混合
version  恰好 +1                          +2 就意味着两次写入都落库
```

### 5. 入口体积上限：配置合理且确实被执行

| 路由 | 上限 |
|---|---|
| 全局 | 16 MB |
| `/api/auth/login`、`/api/auth/register` | **4 KB** |
| `/api/security/unlock`、`/api/account/password` | 4 KB |
| `/api/backup/restore` | 64 MB |

普通扫描件（请求体约 2.4 MB）能正常上传；超过 16 MB 被拒。
**注意拒绝方式是直接重置连接（`ECONNRESET`），不是返回 413** ——
服务端拒绝读取整个请求体，这比返回 413 更好（不会先把 16 MB 读进内存）。
因此测试断言的是「没有成功、也没有落库」，而不是某个状态码。

### 6. 审计表规模

`GET /api/audit` 有 `LIMIT 100`，索引 `ix_audit_owner(owner_id, id DESC)`
与查询的 `ORDER BY id DESC` 匹配。表本身只增不删——**对审计日志而言，
保留历史是特性而非缺陷**，故不作为问题处理。

## 四、需要后续处理的一处隐患

**乐观并发保护依赖调度顺序，而不是数据库层的条件更新。**

版本比较在 `mutate()` **之外**完成：先 `getRecord` 拿当前 version 比对，再进事务写入。
这段之所以安全，是因为该处理器里读与写之间**没有任何 `await` 点**，
Node 单线程下没有别的请求能插进来。

也就是说，保护来自「恰好没有 await」，而不是来自 `UPDATE ... WHERE version = ?`。

**将来若有人在读与写之间插入一个 `await`**（比如给日志或审计加一次异步落盘），
窗口会立刻打开 —— 而**现有的两条用例（先后陈旧 + 并发）都可能继续通过**。

建议：把版本条件并入 `UPDATE` 的 `WHERE`，让保护不依赖调度顺序。

## 六、上线前

三条命令只有你能执行（栈根不是 `main`，且三个 PR 是草稿）：

```bash
gh pr edit 1 --base main          # 不接上去，什么都到不了生产
gh pr ready 3
gh pr ready 4
```

之后按 1 → 3 → 4 合并。

服务器上先跑自检，它会按 FAIL 退出：

```
node scripts/preflight.cjs
```

它会检查 `REGISTRATION` 是否显式且合法、`INVITE_CODE` 长度、
`PUBLIC_ORIGIN` 是否 https、`DATA_DIR` 是否可写、数据库能否只读打开并数出
用户/记录/文档数、Node 是否 ≥ 22.16.0。
**另外有 4 项它不谎报**：真实日志抽查、备份恢复演练、Windows 安装包验证、
分批上线观察——这些必须在真实环境里做，脚本只把它们列出来。
